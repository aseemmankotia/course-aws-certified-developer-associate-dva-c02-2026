## Chapter 5: IAM, AWS STS, and Amazon Cognito: Authentication and Authorization — Flashcards

| # | Front (Question) | Back (Answer) |
|---|-----------------|---------------|
| 1 | STS AssumeRole: default / minimum / maximum session duration? | Default 3600s (1h) if DurationSeconds not specified. Minimum 900s (15 min). Maximum up to 43200s (12h), but capped by the role's MaxSessionDuration attribute. Exam tip: requesting a duration above MaxSessionDuration causes the call to fail. |
| 2 | Cognito User Pool: ID/Access token validity range? | Configurable 5 minutes to 24 hours; default 1 hour. Exam tip: short-lived by design — apps must use the refresh token to get new tokens. |
| 3 | Cognito User Pool: Refresh token validity range? | Configurable 60 minutes to 10 years; default 30 days. Exam tip: refresh token is what lets a mobile app avoid re-prompting login for a long period. |
| 4 | IAM inline policy size limits per entity type? | User: 2,048 characters. Role: 10,240 characters. Group: 5,120 characters. Exam tip: managed policies (max 6,144 chars each) are preferred for reuse across entities. |
| 5 | Max managed policies attachable to one IAM user/role/group (default quota)? | 10 managed policies (soft limit, can request increase). Exam tip: exceeding effective policy size across all attached policies is a common design constraint tested via scenario questions. |
| 6 | Cognito User Pool vs Identity Pool — core difference? | User Pool = authentication (who the user is): directory, sign-up/sign-in, MFA, issues JWTs. Identity Pool = authorization to AWS (what the user can access): federates an identity (User Pool, social IdP, SAML, or unauthenticated) into temporary AWS credentials via STS. |
| 7 | Identity-based policy vs resource-based policy? | Identity-based: attached to a user/group/role, NO Principal element (the principal is implicit — whoever holds the identity). Resource-based: attached to a resource (S3 bucket, KMS key, Lambda, SQS queue), MUST include a Principal element, and enables cross-account access without role assumption. |
| 8 | IAM user vs IAM role — key exam distinction? | IAM user: long-term credentials (access key/secret), persistent identity. IAM role: no long-term credentials, has a trust policy defining who can assume it, and issues temporary credentials via STS when assumed. Exam best practice: prefer roles for workloads (EC2, Lambda, cross-account access). |
| 9 | Cross-account S3 access pattern — what must exist on BOTH sides? | Caller's account: identity-based policy on the IAM role/user allowing the S3 action. Resource account: bucket policy (resource-based) explicitly allowing that role/user's ARN. Missing either side = access denied. |
| 10 | Mobile app → temporary AWS credentials pattern (no long-term keys in app)? | App authenticates user (Cognito User Pool, Facebook, Google, or SAML) → passes token to Cognito Identity Pool → Identity Pool calls STS AssumeRoleWithWebIdentity (or AssumeRoleWithSAML) → temporary AWS credentials scoped by an IAM role are returned to the app. |
| 11 | Policy evaluation order in AWS IAM? | 1) Explicit Deny anywhere (identity policy, resource policy, SCP, permissions boundary) → denied, full stop. 2) Explicit Allow (if no deny found) → allowed. 3) No matching statement → implicit deny (default). Exam tip: Deny ALWAYS wins over Allow, regardless of policy type. |
| 12 | AWS CLI syntax to assume a role for 2 hours? | aws sts assume-role --role-arn arn:aws:iam::123456789012:role/MyRole --role-session-name mySession --duration-seconds 7200 Exam tip: role's MaxSessionDuration must be ≥7200 or the call fails. |
